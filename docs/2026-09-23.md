## 13:40 — Дочистка цепочки моделей: почему часть ответов падала

Поведенческая проверка `tools/check_chat_behaviour.py` показала, что 2 запроса из 8
вернули общую ошибку «Что-то пошло не так». Разобрался прямым прогоном `/api/chat`
(`tools/probe_chat_api.py`, новый): один запрос занял **ровно 80.2 с** — это
`Ai:TotalTimeoutSeconds`. То есть медленная запасная модель съедала весь бюджет,
и посетитель через 80 секунд ожидания получал бессмысленную заглушку.

Три правки в `Services/Ai/EloraAssistant.cs`:

1. **`ExplainStatus` не знал про 503.** Перегрузка бесплатного тарифа
   (`Service temporarily overloaded`) попадала в ветку `_ =>` и превращалась в
   «Что-то пошло не так». Добавлена ветка 503/502/504/500 с человеческим текстом.
2. **Причина отказа терялась.** Цепочка возвращала *последнюю* неудачу, а ею часто
   оказывалась заглушка. Теперь запоминается `bestFailure` — первый отказ, который
   что-то объясняет; `IsGenericFailure()` отличает заглушку от осмысленного текста.
3. **Бюджет тратился на заведомо провальный запуск.** Константа
   `MinSecondsToStartModel = 10`: если от бюджета осталось меньше, запасные модели
   не запускаются вообще.

Плюс `AttemptsPerModel` 2 → 3 (`appsettings.json` и `AiOptions`): основная модель
отвечает за ~2 с, поэтому лишний быстрый повтор дешевле ожидания медленной запасной.

**Заодно починены устаревшие значения по умолчанию в `AiOptions`** — там жила
`nvidia/llama-3.1-nemotron-70b-instruct` (этот ключ её не обслуживает) и
`MaxAnswerTokens = 400` (мало: размышления вытекают в ответ). Если бы из
`appsettings.json` убрали цепочку, приложение уехало бы на нерабочую модель.

Результат: `tools/probe_chat_api.py` — **8 из 8**, суммарно 24 с вместо 1 м 47 с;
в логе сервера ноль предупреждений `AI-консультант`, то есть основная модель
отработала без единого переключения. `verify_chat_live.js` — без проблем,

`HTTP 302 → /Admin` (вход выполнен), прежние `admin` / `elora2026` → «не пустило».
То есть секреты работают, и пароль по умолчанию не выживает. Имена переменных
читает `Data/Seed.cs` (строки 36–37).

**Нашёл и починил кодировку логов.** В логе продакшена строка от `LoginModel` не
читалась: байты `8d a5 e3 a4 a0 e7 ad a0 ef` — это **CP866**, а не UTF-8. Проверил
все логи: в `_server_run22.log` 23 строки с кириллицей не в UTF-8, то есть **вся**
русская часть лога. Причина: на русской Windows `Console.OutputEncoding` = OEM-кодовая
страница, и при перенаправлении в файл кириллица пишется в CP866. В терминале это
выглядит нормально (терминал в той же кодировке), а в редакторе — кракозябры.

Лечение в `Program.cs` (перед `WebApplication.CreateBuilder`):

```csharp
if (Console.IsOutputRedirected)
{
    try { Console.OutputEncoding = Encoding.UTF8; }
    catch (IOException) { }
}
```

Только для перенаправленного вывода: в живой консоли кодировку задаёт пользователь,
и ломать её не наше дело. `try/catch` обязателен — без консоли сеттер бросает
`IOException` и уронил бы старт. На Linux (и на хостинге) это no-op.
Проверено на `EloraRun23`: 3 строки кириллицы, все в UTF-8, не-UTF-8 — 0.

**Уточнил правило про Smart App Control.** У `EloraRun23` заблокирован оказался
**`.exe`-apphost** (`Permission denied` при выключенной песочнице), а
`dotnet EloraRun23.dll` пошёл сразу — раньше было наоборот. Значит, ни один из двух
файлов не «тот, который работает»: порядок попыток `.exe` → `.dll` → новое имя.
Поправил память и навык `aspnet-razor-admin-verify` (там же уточнил, что
`taskkill` в Git Bash работает с `MSYS_NO_PATHCONV=1`, и добавил раздел про CP866).

Итог: `verify_site_live.js` — **201 проверка, 0 ошибок**, `verify_ai_live.js` —
без проблем, `verify_chat_live.js` — без проблем. Рабочий сервер `EloraRun23`

## 14:05 — Хостинг: Fly.io отпал, выбран бесплатный .NET-хостинг

Пользователь сообщил, что попробовал Fly.io и там оказался платный тариф, и попросил
перейти на бесплатное — «Vercel, Render, Neon». Проверил по документации провайдеров
(поиск + чтение страниц), и часть плана пришлось скорректировать:

- **Fly.io** — пользователь прав: новым аккаунтам дают только пробный период
  (2 часа VM или 7 дней), дальше требует карту. Бесплатного тарифа фактически нет.
- **Vercel** — Hobby разрешён **только для личного некоммерческого использования**
  (fair use guidelines), то есть сайт студии под него не подпадает, нужен Pro $20/мес.
  Плюс технически: у контейнера нет постоянного диска; лимит тела запроса 4.5 МБ
  (сломал бы загрузку картинок в админке); **фоновые службы останавливаются между
  запросами** — «There's no process when there's no traffic», то есть `TelegramPollingService`
  с длинным опросом на Vercel не работает вообще. .NET там запускается только как
  контейнер через `Dockerfile.vercel` + `runtime: "container"`.
- **Render free** — 750 ч/мес, засыпает через 15 минут простоя, а **постоянный диск
  только на платном тарифе** (это прямо в их документации). Значит SQLite стирается
  при каждом деплое/перезапуске, данные клиентов теряются.
- **Neon free** — 0.5 ГБ, ~100 вычислительных часов в месяц. Хватит, но если приложение
  держит соединение к базе открытым круглосуточно, часы кончатся в середине месяца.

**Вывод, который я донёс до пользователя:** чтобы было бесплатно и без потери данных,
надо увозить базу в Neon и переписывать слой данных с SQLite на Postgres (`$name`-параметры,
`last_insert_rowid()`, `AUTOINCREMENT`, `datetime('now')` — всё иначе). Поэтому предложил
варианты и спросил выбор; пользователь ответил «расскажи про бесплатный хостинг, моя цель
чтобы по ссылке открывалось и работало».

**Выбран бесплатный хостинг .NET на Windows/IIS** (MonsterASP.NET): `имя.runasp.net`,
бесплатный HTTPS, .NET 10 поддерживается, карта не нужна, **переписывать ничего не надо** —
SQLite, оба бота и напоминания работают как есть. Ограничения, о которых сказал сразу:
своего домена на бесплатном тарифе нет (только поддомен), пул IIS выгружается при простое,
то есть боты спят вместе с сайтом (заявки при этом не теряются).

Что сделано:

- `ELORA_agent_docs/DEPLOY_FREE.md` — пошаговая инструкция: почему не Vercel/Render/Fly,
  что нужно от пользователя, сборка, загрузка (FTP/Web Deploy/GitHub), переменные
  окружения, что проверять, диагностика (включение stdout-лога IIS), честные ограничения.
  Отдельно подчёркнуто: **`ELORA_ADMIN_LOGIN`/`PASSWORD` задать ДО первого открытия сайта** —
  админ пишется в базу один раз.
- `tools/publish_for_host.sh` — собирает пакет и пакует в zip, с проверкой, что не уехали
  `.env`, ключ и база. На выходе `_upload_elora` (64 МБ, 432 файла) и `elora_site.zip` (29 МБ).
- `web.config` для IIS `dotnet publish` генерирует сам — руками писать не надо.

**Три грабли, пойманные по ходу:**

1. Скрипт сразу нашёл, что в публикацию уезжает `appsettings.Development.json`
   (там `DetailedErrors: true`). Секретов нет, но если хостинг случайно выставит
   окружение Development, посетители увидят стек ошибок. Исключил файл из Release
   в `ELORA.Web.csproj` через `<Content Update ... CopyToPublishDirectory=Never>`.
2. **`set -o pipefail` + `grep` обрывал скрипт ровно в хорошем случае:** `grep` без
   совпадений возвращает 1, и проверка «ключ не найден» убивала сборку. Переписал
   проверки через `if grep -q`.
3. Массовое `rm -rf` папки сборки (433 файла) заблокировал гвард безопасности.
   Скрипт переделан: папку не удаляет, а точечно убирает только лишние файлы —
   так и надёжнее. Ещё: `zip` в Git Bash нет, а `powershell.exe` из bash вызывать
   нельзя («bypasses PowerShell security checks») — пакуем через питон.

**Проверено:** собранный пакет запущен в Production на порту 8092 со свежей базой —
`/`, `/healthz`, `/services`, `/faq`, `/booking`, `/admin/login` отдают 200, AI отвечает,
`.env` и `appsettings.Development.json` в пакете отсутствуют. Временные папки убраны,
рабочий сайт на 5080 жив.

`SqliteConnectionFactory` **сама создаёт папку** под файл базы (`Directory.CreateDirectory`
на строке 28) и открывает с `ReadWriteCreate`, поэтому пустой `App_Data` в пакете —
не проблема, база появится при первом запросе.

## Развёртывание на бесплатный хостинг — сайт заработал

`http://elora2026.runasp.net` поднят. Что сделано и что мешало:

- Собрал пакет и залил по FTP. Первые прогоны падали с
  `550 Could not get file: driver error: calling GetHandle: file does not exist` —
  оказалось, `exists()` в скрипте заливки делал `cwd(remote)`, а при неудаче всё равно
  выполнял `cwd("..")`, что **уводило сессию из `/wwwroot` в корень**. Папки создавались
  не там. Починил: запоминать текущий каталог и возвращаться в него в `finally`.
- Вторая ошибка: заливал в корень FTP `/`. IIS запускает приложение из
  `D:/Sites/site93502/wwwroot`, то есть из `/wwwroot`. Заливка в корень даёт 403/404.
- Дальше `DllNotFoundException: e_sqlite3` — в `deps.json` цель рантайма была без RID,
  и нативная библиотека не находилась. Пересобрал с `-r win-x64`, но получил
  `500.30` и в логе `The assembly architecture is not compatible with the current
  process architecture`. **Пул хостинга 32-битный**, нужна сборка `-r win-x86`.
- Лог при `hostingModel="inprocess"` не писался вообще. Переключение на
  `hostingModel="outofprocess"` дало ошибку в `logs\stdout_*.log` — так и нашлась
  разрядность.
- После сборки под `win-x86` — 200 на всех страницах. Проверено: админка своим логином
  (старые `admin`/`elora2026` отклоняются), AI-консультант 8 из 8 за ~2 с, тестовая
  запись создалась (потом отменена), статика отдаётся.
- Прибрал: мусор из корня FTP, остатки прошлых попыток в `/wwwroot` (в т.ч. папку `refs`
  на 307 файлов и `runtimes`), лог отладки выключил.
- Инструменты: `tools/sync_ftp.py` (инкрементальная выкладка), `tools/publish_for_host.sh`
  переведён на `win-x86`. Грабли записаны в `MONSTERASP_STEPS.md`, раздел «Практика».
- **Осталось за пользователем:** включить SSL-сертификат в панели (HTTPS пока не
  работает), сменить пароль FTP (он засветился в переписке), при желании добавить
  токены Telegram-ботов.
