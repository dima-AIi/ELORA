## Поздний вечер: нейросетевой апскейл (EDSR x4)
Пользователь: «на /works фото размытые, подправь и их тоже». Причина не в размере файла
(680×714 при нужных 641 для карточки 320 css), а в ИСХОДНИКЕ: ячейка макета даёт всего
**130×137**, то есть 5-кратное увеличение. Пошаговый LANCZOS такое не вытягивает.

**Решение:** `cv2.dnn_superres` + модель EDSR x4 (`tools/models/EDSR_x4.pb`, 38 MB,
скачана с GitHub Saafke/EDSR_Tensorflow). Это свёрточная сеть, она восстанавливает кромки,
а не интерполирует. Содержание кадра не меняется — только чёткость.
- `opencv-contrib-python-headless` 5.0.0 поставлен в managed-venv.
- Новый `tools/build_sr.py <works|services|all>`: тот же крой, что в `build_images.py`,
  но апскейл через EDSR, потом доводка до целевого размера и СЛАБЫЙ unsharp
  (radius 1.0, percent 42) — сильный поверх сети рисует ореолы на ресницах.
- `tools/build_hero.py` переведён на EDSR: 284×312 -> 1136×1248, дальше кроп до 1098×1206.
  Старый пошаговый LANCZOS оставлен запасным путём, если x4 не хватило.
- Тайминг на CPU: 130×137 ≈ 13 с, 275×288 ≈ 78 с. Весь прогон (14 работ + 6 услуг + hero)
  ≈ 20 мин, поэтому только фоново.

**Результат:** сравнение 1:1 на реальной странице — работы заметно чётче (ресницы по волоскам,
пряди волос, кромка ногтя, фактура кожи). Hero чище, без блочности LANCZOS. Итог по файлам:
hero 235 KB, услуги 309 KB, работы 718 KB, мастера 410 KB, промо 259 KB — всего 1964 KB.
`verify_pages.js` (desktop + mobile390 × 8 страниц) — 16/16 ok, broken=0.

**Что осталось потолком:** hero-девушка всего 284 px исходника -> 1098 px, это 3.9×.
Сеть убрала блочность, но настоящей детализации там взяться неоткуда. То же для работ
(130 px). Если пользователь захочет по-настоящему резкие фото — нужна замена на реальную
съёмку/сток того же содержания.

### Три бага, найденных при первом запуске с настоящим токеном
1. **КРИТИЧНО: сайт падал целиком.** `TelegramService.CallAsync` строил ОТНОСИТЕЛЬНЫЙ адрес
   `$"bot{_token}/{method}"` при `BaseAddress = https://api.telegram.org/`. Токен содержит
   двоеточие (`8913562021:AA…`), поэтому .NET разбирал `bot8913562021:AA…/getMe` как URI
   со схемой `bot8913562021` → `NotSupportedException: The 'bot8913562021' scheme is not
   supported`. Исключение не попадало в фильтр `catch (ex is HttpRequestException or
   TaskCanceledException or JsonException)`, вылетало из `BackgroundService`, а
   `HostOptions.BackgroundServiceExceptionBehavior` по умолчанию = `StopHost` → **хост
   останавливался вместе с сайтом**. Лечение: адрес только абсолютный
   (`https://api.telegram.org/bot{token}/{method}`), `catch (Exception)` целиком, плюс
   `Configure<HostOptions>(o => o.BackgroundServiceExceptionBehavior = Ignore)` в `Program.cs`.
   Имя бота на старте polling тоже обёрнуто в try/catch.
2. **Токен утекал в логи.** `System.Net.Http.HttpClient` логирует полный URL с токеном на
   уровне Information, а в `appsettings.Production.json` `Default: Information`. Добавил
   `"System.Net.Http.HttpClient": "Warning"`.
3. **Бесполезная диагностика теста.** Кнопка «Отправить тестовое сообщение» писала «проверьте
   токен и Chat ID», хотя самая частая причина другая — человек не нажал Start у бота.
   Добавил `TelegramService.SendTestAsync`, который возвращает причину из Telegram и переводит

## Сквозная проверка Telegram (после «нажал старт»)

Пользователь нажал Start → тестовое сообщение ушло. Дальше прогнал полный сценарий записи
через реальный интерфейс (`tools/e2e_booking.js`, новый) и нашёл ещё две настоящие проблемы.

### Найдено и исправлено

4. **Длинный опрос молча не работал.** `TelegramService` задавал `_http.Timeout = 20 с`, а
   `GetUpdatesAsync` просит у Telegram `timeout=25` — сервер держит соединение 25 с, общий
   лимит обрывал запрос РАНЬШЕ ответа, всегда. В логе была лестница
   `TaskCanceledException: canceled due to the configured HttpClient.Timeout of 20 seconds`.
   Симптом: уведомления ходят, а бот не получает ни команд, ни нажатий кнопок.
   Лечение: `_http.Timeout = Timeout.InfiniteTimeSpan`, таймаут задаётся точечно в `CallAsync`
   (короткие вызовы 20 с, опрос — `timeoutSeconds + 15`); `OperationCanceledException` со
   фильтром `when (!ct.IsCancellationRequested)` отделён от остановки приложения.
5. **Deep-link без `?start=` — привязка клиента не работала.** `BookingSuccess.cshtml.cs`
   строил ссылку из одного `Telegram.BotUsername`, а код привязки (создаётся в
   `BookingService.CreateAsync` и возвращается в JSON ответа POST) до страницы успеха не
   доходит — она открывается отдельным GET после редиректа. Бот получал обычный `/start`
   без параметра и отвечал общим текстом. Добавил
   `BookingRepository.GetOrCreateLinkCode(clientId, bookingId)` (возвращает неиспользованный
   код или создаёт новый) и использование его на странице успеха; плюс ветка
   `TelegramConnected` — если клиент уже привязан, кнопки нет, есть строка «Telegram подключён».
6. **`System.Net.Http.HttpClient: Warning` добавлено и в базовый `appsettings.json`** — токен
   утекал в логи и в Development.
